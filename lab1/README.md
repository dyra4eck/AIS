# Лабораторная работа 1. Оптимизация, обеспечиваемая ключом GCC

## 1. Вариант задания

**Вариант 7 — `-fbranch-probabilities`.**

Разработать программу, которая позволит продемонстрировать оптимизацию,
обеспечиваемую ключом оптимизации gcc `-fbranch-probabilities`.

Среда выполнения: GCC 13.3.0 (Ubuntu 24.04), x86-64, Intel Xeon @ 2.80 GHz (виртуальная машина).

## 2. Описание ключа оптимизации

Компилятор принимает много решений исходя из того, какая ветвь условного перехода
выполняется чаще: какой блок поставить «прямо» (fall-through), а какой — вынести
по переходу, заменять ли короткое ветвление командой условной пересылки `cmov`,
какой код считать «холодным», что выравнивать, какие переменные держать в регистрах и т.д.

По умолчанию (при `-O1` и выше) вероятности ветвлений **угадываются** статическими
эвристиками (`-fguess-branch-probability`): например, «значение, скорее всего,
неотрицательно», «сравнение на равенство скорее ложно», «`continue` в цикле
выполняется редко», «цикл делает около 10 итераций». Если реальные данные устроены
иначе, компилятор оптимизирует не ту ветвь.

Ключ `-fbranch-probabilities` заставляет GCC использовать **измеренные** вероятности.
Работа идёт в два этапа:

1. Программа компилируется с `-fprofile-arcs`: в код добавляются счётчики дуг графа потока
   управления. При запуске на типичных данных счётчики сохраняются в файл `*.gcda`.
2. Программа перекомпилируется с `-fbranch-probabilities`: компилятор читает `*.gcda`,
   проставляет каждому переходу реальную вероятность (примечание `REG_BR_PROB` в RTL)
   и реальные счётчики выполнения каждому базовому блоку.

Далее эти данные используют уже включённые проходы оптимизатора, в первую очередь:

* **переупорядочивание базовых блоков** (`-freorder-blocks`) — горячий путь
  располагается последовательно, без лишних переходов;
* **разделение функции на горячую и холодную части** (`-freorder-blocks-and-partition`) —
  функции, выполнявшиеся часто, помещаются в секцию `.text.hot`, никогда не выполнявшиеся
  участки выносятся в `.text.unlikely` (функция `имя.cold`);
* **if-conversion** — замена ветвления на `cmov` выполняется только тогда, когда ветвление
  плохо предсказуемо; ветвление с вероятностью, близкой к 0 или 1, считается хорошо
  предсказуемым и остаётся переходом;
* распределение регистров, выравнивание, развёртка циклов и т.п.

Особенности:

* ключ имеет смысл только вместе с оптимизацией (`-O1`/`-O2`/`-O3`): при `-O0` проходы,
  использующие вероятности, не работают;
* профиль должен быть собран с теми же ключами оптимизации и для того же исходного
  текста, иначе GCC выдаст предупреждение о несовпадении профиля;
* файл профиля ищется по имени выходного файла: при `-o main_bp.o` (или `-o main_bp.s`)
  читается `main_bp.gcda`;
* в отличие от `-fprofile-use`, ключ `-fbranch-probabilities` **только** подключает профиль,
  не включая дополнительно `-funroll-loops`, `-fpeel-loops`, `-ftracer`, `-fvpt` и др.
  Поэтому различия в коде обусловлены именно информацией о вероятностях ветвлений.

| [`run_output.txt`](run_output.txt) | результат работы `run.sh` |

Идея программы: функция `process` обходит массив из 4096 чисел, при этом ветвления
написаны так, что статические эвристики GCC ошибаются. Массив заполняется
детерминированным генератором (LCG), поэтому тренировочный и рабочий запуски
обрабатывают одинаковые данные: 98% элементов равны `-1000`, по 1% — случайные
положительные и случайные отрицательные числа.

```c
__attribute__((noipa))   /* запрет межпроцедурных оптимизаций: вызов не будет вынесен из цикла */
long process(const int *a, int n)
{
    long sum = 0;
    for (int i = 0; i < n; i++) {
        int x = a[i];
        if (x < 0) {                /* эвристика: 41%,  на деле ~99%          */
            sum += -x;
            if ((x & 1) == 0)       /* эвристика: 50%,  на деле ~99.5%        */
                sum ^= x;
        } else {                    /* эвристика: 59%,  на деле ~1%           */
            sum += x * 7;
            sum = (sum << 3) | (sum >> 60);
        }
        if (x == -1000)             /* эвристика: 20%,  на деле ~98%          */
            continue;
        sum += i;
    }
    return sum;
}
```

Время выполнения 2000 вызовов `process` (8 192 000 итераций цикла) измеряется счётчиком
тактов TSC командами `CPUID; RDTSC` … `RDTSCP; CPUID`, как рекомендовано в методических
указаниях. Атрибут `noipa` нужен, чтобы GCC, поняв, что функция «чистая» и данные не
меняются, не вычислил её один раз вместо 2000 (без него замер показывал ~19 000 тактов).

Полный текст — в файле [`main.c`](main.c).

### Сборка и запуск

```bash
./build.sh          # профиль, main_O2.s / main_bp.s, main_O2 / main_bp
meld main_O2.s main_bp.s
./run.sh 20         # 20 чередующихся запусков каждой версии + статистика
```

Команды, которые выполняет `build.sh`:

```bash
# 1. сборка с инструментированием и тренировочный запуск -> main_prof.gcda
gcc -O2 -fprofile-arcs -ftest-coverage -c main.c -o main_prof.o
gcc -fprofile-arcs main_prof.o -o main_prof
./main_prof
cp main_prof.gcda main_bp.gcda

# 2. ассемблерный код без ключа и с ключом
gcc -O2                        -masm=intel -S main.c -o main_O2.s
gcc -O2 -fbranch-probabilities -masm=intel -S main.c -o main_bp.s

# 3. исполняемые файлы
gcc -O2 -Wa,-mbranches-within-32B-boundaries main.c -o main_O2
gcc -O2 -Wa,-mbranches-within-32B-boundaries -fbranch-probabilities -c main.c -o main_bp.o
gcc main_bp.o -o main_bp
```

Базой для сравнения выбран `-O2`, а не `-O0`: без оптимизации компилятор вероятности
ветвлений не использует, и ключ ни на что бы не повлиял.

## 5. Описание найденных различий и их обоснование

### 5.1. `cmove` заменена условным переходом (главное различие)

Без профиля условие `(x & 1) == 0` получает оценку 50% — ни одна эвристика к нему
не подходит. Переход с вероятностью 50/50 процессор предсказывать не сможет, а каждое
неверное предсказание стоит 15–20 тактов. Поэтому проход if-conversion заменяет его
командой условной пересылки: сумма вычисляется в `rcx` безусловно, затем `cmove rax, rcx`.

С профилем GCC знает, что условие истинно в 99.5% случаев. Такой переход считается
хорошо предсказуемым (`predictable_edge_p`), и замена на `cmov` не выполняется:
остаются `test al, 1` / `jne .L4` и `xor rdx, rsi`.

Почему это быстрее: переменная `sum` образует цепочку зависимостей между итерациями.
В версии `-O2` на каждой итерации в этой цепочке стоят три последовательные команды:
`add rax, rcx` → `xor rcx, rax` → `cmove rax, rcx` (`cmov` ждёт оба операнда и флаги).
В версии с профилем — две: `add rdx, rsi` → `xor rdx, rsi`; результат проверки
`test al, 1` не нужно ждать, так как процессор предсказывает переход и выполняет
команды спекулятивно, а ошибается он лишь в 0.5% итераций.

Контрольный эксперимент подтверждает, что основную часть ускорения даёт именно это
изменение: `gcc -O2 -fno-if-conversion -fno-if-conversion2` (запрет замены ветвлений
на `cmov`, профиль не используется) даёт код с расположением блоков как в `main_O2.s`,
но с переходом вместо `cmove`, и работает почти так же быстро, как версия с профилем
(см. раздел 6).

### 5.2. Переупорядочивание базовых блоков

Без профиля GCC оценивает ветку `x >= 0` в 59% и считает её основной: блок `.L3`
стоит в начале тела цикла, а «главный» путь для `x < 0` дополнен второй копией
проверки конца цикла (`add rdi, 1 / cmp / jne .L7`).

С профилем блоки расставлены по реальной частоте: горячий путь `x < 0 && x == -1000`
(блоки `.L14` → `.L4` → `.L7`) занимает непрерывный участок кода, в котором на каждую
итерацию выполняется только один переход (`js .L14`), а редкий блок для `x >= 0` и
общий хвост `.L6` (выполняется лишь в 2% итераций) вынесены за пределы горячего цикла.
Заодно поменялось распределение регистров (`rdx`/`rcx` вместо `rax`/`rdi`), так как
распределитель регистров тоже учитывает частоты выполнения блоков.

### 5.3. Разделение на горячую и холодную части

Согласно профилю функция `process` вызывалась 2000 раз и выполняет 8 млн итераций,
поэтому она помещена в секцию `.text.hot`. Ветка `n <= 0` не выполнилась ни разу —
она вынесена в отдельный фрагмент `process.cold` в секции `.text.unlikely`.
Компоновщик группирует горячий код вместе, а холодный — отдельно, благодаря чему
горячий код плотнее занимает кэш команд и TLB.

Без профиля компилятор не знает, какие функции и блоки не выполняются, и такого
разделения не делает.

### 5.4. Изменения в `main`

В цикле заполнения массива без профиля GCC считает редкие варианты (`r == 0`, `r == 1`)
достаточно вероятными: для ветки `r == 1` он дублирует хвост цикла (своя запись в массив
и своя проверка конца цикла `cmp rdi, rsi / jne .L19`), чтобы сэкономить переход.
С профилем GCC знает, что эти ветки выполняются лишь в 1% итераций, поэтому
оптимизирует их по размеру: без дублирования, отдельными блоками (`.L24` и блок после
`jne .L16`), которые возвращаются к общей записи `.L17` командой `jmp`.
Цикл стал короче, а частый путь (`data[i] = -1000`) не изменился по числу команд.
Остальные изменения в `main` (номера меток, выбор регистров) являются следствием этого.

## 6. Оценка времени работы программы

Скрипт `run.sh` 20 раз запускает обе версии, чередуя их (`-O2`, с ключом, `-O2`, с ключом, …),
чтобы всплески фоновой нагрузки влияли на обе версии одинаково, и вычисляет статистику.
Время — число тактов TSC на 2000 вызовов `process` (8 192 000 итераций).
Полный вывод — в файле [`run_output.txt`](run_output.txt).

|                              | min        | медиана    | среднее    | max        |
|------------------------------|-----------:|-----------:|-----------:|-----------:|
| `-O2`                        | 27 552 602 | 28 290 525 | 29 301 784 | 43 792 996 |
| `-O2 -fbranch-probabilities` | 23 829 172 | 24 336 496 | 24 699 790 | 28 583 960 |

**Ускорение: 1.16 раза** по минимуму и по медиане (1.19 по среднему, которое сильнее
искажено выбросами). В пересчёте на одну итерацию: ~3.45 такта против ~2.97 такта.

Замечание о выравнивании переходов. Процессоры Intel начиная со Skylake (ошибка JCC erratum)
не помещают в кэш микроопераций переходы, пересекающие границу 32 байт. В версии с ключом
пара `cmp rdi, rcx / je .L1` без выравнивания оказалась ровно на такой границе, и результаты
стали зависеть от случайного расположения кода. Поэтому исполняемые файлы обеих версий
собираются с `-Wa,-mbranches-within-32B-boundaries` (ассемблер сдвигает переходы, не меняя
команды; файлы `.s` при этом не меняются). Без этого ключа (`JCC_FIX= ./build.sh`)
обе версии работают медленнее (~44 и ~37 млн тактов), но соотношение сохраняется: ~1.17 раза.

Контрольный эксперимент (раздел 5.1), 8 чередующихся запусков, медиана:

| Вариант | Медиана, тактов |
|---------|----------------:|
| `-O2` | ~28.5 млн |
| `-O2 -fno-if-conversion -fno-if-conversion2` | ~25.2 млн |
| `-O2 -fbranch-probabilities` | ~24.6 млн |

То есть около 80% выигрыша даёт отказ от `cmov` (раздел 5.1), остальное —
переупорядочивание блоков и распределение регистров (раздел 5.2).

## 7. Выводы

1. Ключ `-fbranch-probabilities` заменяет угадываемые эвристиками вероятности ветвлений
   на измеренные при тренировочном запуске программы, собранной с `-fprofile-arcs`.
   Сам по себе он новых преобразований не добавляет — он даёт существующим проходам
   (`-freorder-blocks`, `-freorder-blocks-and-partition`, if-conversion, распределение
   регистров) точные данные, поэтому использовать его имеет смысл вместе с `-O1`/`-O2`/`-O3`.
2. На демонстрационной программе видны все основные эффекты: горячий путь
   размещён последовательно, никогда не выполнявшийся код вынесен в `process.cold`
   (секция `.text.unlikely`), горячая функция помещена в `.text.hot`, а хорошо
   предсказуемое ветвление не заменено на `cmov`.
3. Версия с ключом работает быстрее в ~1.16 раза. Наибольший вклад (около 80% выигрыша)
   дал отказ от `cmov`: цепочка зависимостей по переменной `sum` сократилась с трёх
   команд до двух; остальное дало расположение блоков по реальной частоте.
4. Выигрыш зависит от того, насколько данные тренировочного запуска похожи на реальные.
   Если бы в рабочих данных условие `(x & 1) == 0` стало случайным (50/50), версия
   с условным переходом, наоборот, проиграла бы из-за ошибок предсказания. Поэтому
   профиль следует собирать на типичных входных данных и обновлять при изменении
   программы.
5. Измерения на современном процессоре требуют аккуратности: результаты зависят от
   фоновой нагрузки (нужны многократные чередующиеся запуски и медиана/минимум) и от
   микроархитектурных эффектов вроде JCC erratum, которые могут дать разницу, сравнимую
   с эффектом исследуемого ключа.
